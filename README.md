# Geriatric Readmission Prediction

## Overview

A hospital readmission occurs when a patient returns to a hospital after discharge. Readmissions can indicate gaps in post-discharge care, care coordination, or treatment effectiveness. In the United States, unplanned readmission events are also used as a healthcare quality metric, and avoidable readmissions represent a significant financial burden.

This project demonstrates an end-to-end machine learning workflow for predicting whether a patient is likely to be readmitted within **30 days** of an inpatient discharge. It uses **synthetic patient data** generated by [Synthea](https://github.com/synthetichealth/synthea), so it can be used for experimentation without exposing protected health information.

Although the repository is named *Geriatric Readmission Prediction*, the supplied Synthea workflow includes a broad synthetic population. The code is intended as a healthcare machine learning demonstration rather than a clinically validated geriatric screening tool.

## Problem statement

Given a patient's inpatient encounter and available historical healthcare records, classify the encounter as likely or unlikely to result in a readmission within 31 days.

The binary target is:

- **Y** — an inpatient encounter is followed by another inpatient encounter within 31 days
- **N** — no qualifying readmission is observed

This is a binary classification problem:

```text
Clinical and demographic history → Readmission risk model → Y or N
```

The positive class is defined from consecutive inpatient encounters. Feature calculations consider each patient's history before the inpatient index date, including a 6-month or 12-month lookback window where appropriate.

## Why it matters

Predicting potential readmissions can help healthcare organizations:

- Identify high-risk patients before or shortly after discharge
- Improve care coordination and post-discharge follow-up
- Prioritize outreach, medication review, and chronic care management
- Understand which clinical factors may be associated with readmission risk
- Reduce avoidable readmissions and the associated cost and resource burden

This repository is an educational proof of concept. Its predictions must not be used for clinical decisions without further validation, fairness analysis, privacy review, and regulatory approval.

## Outcome

The completed modeling dataset contains:

- **26,596 patient records**
- **23,007 negative / non-readmission records (N)**
- **3,589 positive / readmission records (Y)**
- A **wide feature matrix with more than 1,200 modeled columns**

The feature-combination notebook creates a 1,207-column dataframe, and the model-building workflow performs one-hot encoding to produce a 1,210- or 1,211-column dataframe depending on how ID and target columns are counted. Oracle ADS subsequently reports 1,173 columns after its preprocessing step.

Oracle AutoML selected **LightGBM / `LGBMClassifier`** as the model for this binary classification task. The model was then packaged as an OCI Data Science model artifact, verified against test observations, and prepared for deployment.

> The repository records model execution and deployment outputs, but it does not publish a complete clinical validation report or externally validated performance metrics. Accuracy, sensitivity, specificity, calibration, and subgroup performance should be measured on a representative holdout dataset before any real-world use.

## Project workflow

```text
Synthea synthetic CSVs
        ↓
Oracle Autonomous Data Warehouse
        ↓
Inpatient encounter and readmission labels
        ↓
Clinical feature engineering
        ↓
Combined patient-level feature table
        ↓
Oracle Data Science / AutoML
        ↓
LightGBM classifier and deployment artifact
```

### 1. Data loading

`data_prep/001_load_tables.sql`:

- Creates an Oracle database credential for object storage
- Creates ADW tables for Synthea datasets
- Loads the CSV files from Oracle Object Storage

The loaded source tables include allergies, care plans, claims, conditions, devices, encounters, immunizations, medications, observations, patients, and procedures.

### 2. Readmission labeling

`feature_extract/002_create_features.sql`:

- Filters encounters to identify inpatient admissions
- Orders encounters chronologically for each patient
- Calculates the time between successive inpatient visits
- Uses a less-than-31-day interval to define a readmission case
- Creates separate positive and negative patient samples
- Builds a single `rap_table` containing the `READMISSION` target

### 3. Feature engineering

The SQL workflow creates patient-level features from:

- Allergies
- Care plans
- Claim diagnoses
- Chronic conditions
- Medical devices
- Encounter history over 6 and 12 months
- Immunizations
- Medication usage and dispensing duration
- Patient demographics
- Procedures
- Inpatient duration

The design uses one-hot or count-style representations for many coded healthcare concepts. Age, race, ethnicity, and gender are also derived or loaded for the patient cohort.

### 4. Feature combination

`feature_extract/003_combine_features.ipynb`:

- Connects to Oracle Autonomous Data Warehouse
- Exports the engineered tables as CSV files
- Reads the readmission table and feature tables
- Pivots coded categories into patient-level columns
- Merges all feature groups using the patient identifier
- Produces `RAP_DF.csv` for model training

The sample table contains 23,007 patients without a qualifying readmission and 3,589 patients with a qualifying readmission.

### 5. Model training and deployment

`model_build/004_build_model.ipynb`:

- Loads `RAP_DF.csv`
- Separately identifies numerical and categorical columns
- Applies one-hot encoding to `READMISSION`, `RACE`, `ETHNICITY`, and `GENDER`
- Converts the pandas dataframe into an Oracle ADS dataset
- Splits the data into training and test sets
- Uses Oracle AutoML with a 600-second training budget
- Selects `LGBMClassifier` with balanced class weights
- Prepares a model artifact for OCI deployment
- Saves and deploys the model
- Verifies inference on a small test sample

## Running the project

This repository implements an OCI workshop workflow; it is not a standalone local application.

### Prerequisites

You need:

- Access to an Oracle Autonomous Data Warehouse instance
- Oracle Object Storage access to Synthea files
- An Oracle ADW wallet and database credentials
- An OCI Data Science notebook session
- Oracle ADS and the required `generalml_p37_cpu_v1` conda environment
- Resource principal or equivalent OCI authentication

### Workflow

1. Load the Synthea data by running `data_prep/001_load_tables.sql` in ADW.
2. Run `feature_extract/002_create_features.sql` to create the readmission labels and feature tables.
3. Open `feature_extract/003_combine_features.ipynb` in OCI Data Science and update the database connection values as needed.
4. Run the notebook to export feature tables and create `feature_csvs/RAP_DF.csv`.
5. Open `model_build/004_build_model.ipynb` to train, package, verify, save, and deploy the model.

The notebooks expect files and OCI configuration at paths similar to:

```text
/home/datascience/readmission/feature_csvs/
/home/datascience/readmission/Automl_artifacts/
/home/datascience/Wallet_adwck.zip
```

Update these paths for your OCI environment.

## Data and privacy

The project uses [Synthea](https://github.com/synthetichealth/synthea), an open-source tool for generating realistic but synthetic healthcare records. Synthetic data reduces privacy risks, but it does not eliminate the need for data-governance and responsible-machine-learning reviews.

Before adapting this project for real patients:

- Replace synthetic data with an approved healthcare dataset
- Verify encounter and readmission definitions
- Add temporal validation and leakage checks
- Measure calibration and uncertainty
- Evaluate performance across age, sex, race, ethnicity, and socioeconomic groups
- Perform external validation
- Document model limitations and clinical governance requirements

## Limitations

- The data is synthetic and may not reproduce real-world treatment patterns or population biases.
- The 31-day label is a workflow-defined readmission proxy, not a causal measure of preventability.
- The repository contains a broad set of high-dimensional categorical features and may be computationally expensive.
- Notebook credentials, wallet locations, object-storage paths, and OCI resource IDs are environment-specific.
- The workflow does not currently provide a lightweight setup for running locally.
- The final clinical impact has not been measured, and no production validation results are included.
